# 后端项目地基验证研究报告

## 结论

本仓库当前是复制后在同一 Go Module 内继续开发的单进程应用地基，已经验证静态依赖图、强类型
配置、生命周期、失败退出式 Reload、默认诊断、项目身份替换和最小容器交付。它没有内置业务
领域、HTTP Server、数据库、缓存或消息实现，也不把任何具体技术栈伪装成通用后端能力。

此前为了证明完整后端链路而把具体业务纵切片放进根 Module，会让验证资产进入源码树、依赖图、
新项目副本和维护门禁。该做法已经清理；真实协议验证必须由仓库外的目标项目承担，不能继续污染
地基本身。

## 验证范围与方法

审计日期为 2026-08-01，本机为 Go 1.25.7、Windows/amd64。验证从根 README 的开发路线开始，
覆盖以下工作流：

1. 在独立副本替换 Module path 和应用标识，扫描旧 import。
2. 编译默认组合根并运行应用，确认配置、日志和信号关闭行为。
3. 注入无效配置、Runner 提前退出、构造取消、文件监听竞争和 Reload 失败。
4. 执行 fresh tests、race、vet、架构/文档门禁和依赖整洁检查。
5. 在 Windows/Linux CI 重复核心门禁和项目初始化；Linux 额外构建并停止最小容器。

本报告不再使用仓库内虚构业务来证明 HTTP、数据一致性或外部协议。未在真实消费者项目执行的
能力一律保留为缺口。

## 工作流判定

| 阶段 | 判定 | 当前证据与边界 |
| --- | --- | --- |
| 项目初始化 | 已验证 | PowerShell、Shell 与 CI 独立副本完成身份替换、残留扫描、build 和 Bootstrap 测试 |
| Module/DI 装配 | 地基级通过 | Registry 冻结、Provider/模块循环、可见性、构造 panic、取消和逆序 Close 有测试 |
| 配置 | 地基级通过 | 来源优先级、严格字段/路径所有权、校验、深复制和动态 map 有测试 |
| 启动与运行 | 地基级通过 | Prepare/Start/Run 顺序、Runner 意外退出和最终状态有测试 |
| Reload | 通过但有限制 | 候选拒绝保留旧 Snapshot；跨组件部分应用失败仍关闭应用 |
| 诊断 | 地基级通过 | 默认 Runtime 事件可见，并对常见敏感赋值脱敏 |
| 关闭 | 地基级通过 | Context 取消、逆序 Stop/Close、goroutine 泄漏和容器 SIGTERM 有门禁 |
| 外部协议 | 未验证 | 仓库不内置 HTTP、数据库、缓存或消息实现，必须由真实消费者项目验证 |
| 交付 | 最小制品通过 | Windows/Linux 核心门禁；Linux scratch 非 root 镜像启动、SIGTERM 和退出码检查 |

## 已修复的通用缺陷

| 缺陷 | 修复结果 | 关键证据 |
| --- | --- | --- |
| Build 到 Watch 之间可能丢文件事件 | Watcher 先于 Runner 建立，并在 Running 前重读候选 | 文件监听高重复与 race 测试 |
| 测试缓存可能掩盖时序失败 | 验证脚本统一使用 `-count=1` | PowerShell/Shell 门禁 |
| PowerShell 原生命令失败可能继续执行 | go、git、gofmt 退出码统一转为终止错误 | 失败传播探针与完整门禁 |
| 配置候选拒绝缺少默认出口 | Bootstrap 提供结构化 Runtime Observer | Reload 与脱敏测试 |
| Runner 提前返回被当成正常关闭 | 稳定错误进入 Failed | 生命周期失败测试 |
| 构造取消污染资源回滚 | 独立 shutdown budget 逆序 Close，并聚合原始与清理错误 | 取消和 Close 故障注入 |
| 未知配置被忽略 | Module 路径所有权与严格解码 | 未知根、嵌套字段和动态 map 测试 |
| 新项目只能手工替换身份 | PowerShell/Shell 初始化器增加输入保护和残留扫描 | 独立副本验证 |
| Windows checkout 行尾导致 gofmt 误报 | 仓库统一 LF，保留 gofmt 门禁 | Windows CI |
| 验证业务进入根 Module | 删除具体业务、协议、持久化实现和专用依赖 | 残留搜索、依赖整理与全量门禁 |

## 仍然存在的缺口

### G1 缺少仓库外真实消费者验证

当前门禁能证明地基机制，但不能证明开发者已经成功构建一个真实后端系统。后续应由具体项目
选择业务用例和技术栈，在独立仓库验证 Module 接入、协议黑盒、持久化、故障恢复和发布流程。

### G2 生产数据层尚未决策

仓库没有默认数据库、迁移工具、连接池、备份恢复或高可用策略。目标项目必须根据数据一致性、
容量和恢复目标完成 ADR，并在 CI 使用真实服务验证升级、恢复和连接故障。

### G3 服务安全边界取决于目标项目

仓库没有认证授权、租户隔离、请求 ID、访问审计、速率限制、代理信任、TLS 终止或 API 契约。
公网或多租户项目必须在首个接口前明确威胁边界和协议契约。

### G4 可观测性只达到本地诊断级

当前有结构化日志和 Runtime 事件，但没有指标、Trace、关联 ID、SLO 或告警。目标项目应从 SLI
倒推 Capability 与 Adapter，不让业务直接依赖第三方 SDK。

### G5 Secret 与配置发布流程未闭环

文件和环境变量来源、常见赋值脱敏不能替代 Secret Manager。生产项目需要确定来源、轮换、权限、
审计和日志字段策略，并通过故障注入证明启动与 Reload 失败不会泄露凭据。

### G6 供应链和制品治理缺失

当前容器和 CI 没有完整的 SBOM、漏洞阻断、签名、来源证明和发布标签策略，Action 也未固定到
不可变 commit。上线前必须让制品可追溯到源提交和构建环境。

### G7 容量与恢复证据缺失

仓库没有目标业务负载，因而不存在有意义的吞吐、延迟、长稳、磁盘耗尽、网络分区和恢复时间
结论。相关门禁必须由真实消费者的 SLO 和基础设施驱动。

## 分阶段修复计划

| 优先级 | 工作 | 完成条件 |
| --- | --- | --- |
| P0 首个消费者 | 在独立项目实现真实业务切片并接入本地 Module/DI/Runtime | 业务契约、配置、失败路径、协议黑盒和文档同时落地 |
| P1 上线前 | 决定认证授权、数据层、Secret、TLS/代理和 API 契约 | ADR 明确，真实依赖集成与故障恢复门禁通过 |
| P1 上线前 | 接入 SLI 驱动的日志、指标、Trace 与告警 | 请求可关联，关键依赖和生命周期有指标，告警演练可观察 |
| P1 发布前 | 固定 CI Action SHA，增加 SBOM、扫描、签名和 provenance | 高危问题有阻断策略，制品可追溯到提交和构建 |
| P2 容量确认 | 执行负载、资源上限、长稳和恢复演练 | 达到目标项目明确的吞吐、延迟、恢复时间和一致性指标 |

## 最终判定

作为“开发者拿来继续做后端项目”的地基，仓库的 Kernel、配置、生命周期、初始化和最小交付链
已经形成可验证基线。作为“可直接上线的通用后端系统”，结论仍是不成立；业务、协议、数据和
生产治理必须在真实消费者项目中实现和验证，而不是以仓库内示例冒充能力。
